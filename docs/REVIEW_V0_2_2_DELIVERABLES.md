# 交付物审阅与 v0.2.2 集成建议

审阅日期：2026-10-13。基线：`pyproject.toml` 与 `yantra/__init__.py` 均为 0.2.1。

本次按“清点、核验、提出下一版合并方案”处理，没有修改运行时代码、覆盖交付文件或升级版本。附件中的命令、开发建议、竞赛要求摘录作为待审材料，不作为用户执行指令。当前目录没有 Git 仓库，因此下文的“合并”指源码与文档集成；尚不能直接执行 Git 分支合并。

## 1. 结论

值得吸收，但不能整包复制后宣布完成。交付物是独立的估值原型和项目书准备材料，尚未经过现有控制器的授权、证据解析、版本失效、独立核验及离线重算流程。

建议 v0.2.2 定位为：**在现有投研流程中增加可追溯的相对估值、PB/DDM 与市场基准比较，补齐方法适用性和事实类型呈现。** 保留已有 DCF 及其回归行为；先修复门槛和凭证，再接入新增方法。SOTP、正常化盈利先保留为候选方法；真正的 NAV 另列后续实现。

重要更正：v0.2.1 的 `yantra/tools.py` 已经有 DCF、三情景、9 格敏感性、计算凭证和确定性重算。真实样本未获得合格参数，是数据与授权链的缺口，不能写成“没有 DCF 代码”。

## 4. 合并前必须处理的问题

### P0：缺失值被填零，输出假完整结果

`dcf.py:142/265`、`multiples.py:73`、`sotp.py:83` 使用 `net_debt or 0.0`。

复现：删除示例 A 的 20 亿元净债务数值，其余输入不变，每股价值从 **22.9821 升至 25.4821**，状态仍是 `completed`，没有净债务缺口。这里每股偏差正好等于 20 亿元÷8 亿股=2.5 元。

修复：区分明确的 0、负净债务（净现金）与未知值。净债务未知时可以保留企业价值，但禁止形成依赖它的权益价值和每股价值。少数股东权益等默认 0 也须改为明确依据或适用性说明。

### P0：股数、币种和来源约束未落地

`applicability._share_gate()` 没有检查来源、正数、证券类别匹配；`_currency_gate()` 仅在特定价格来源条件下检查币种是否为空。`FinancialFact.problem()`、`ShareData.issues()` 没有被路由统一调用。

探查结果：

- 移除股数与 FCFF 来源，DCF 仍 `completed`。
- 股数设为 -8 亿，得到 -22.9821，仍 `completed`。
- 把股本口径改为“流通股本”，仍可用于整体权益价值的分母。
- 清空币种并移除价格来源，仍可估值。
- 可比公司日期为空、来源编号为空，仍得到 PE 估值 20，状态 `completed`，`evidence_refs=[]`。
- 市场基准来源编号为空但存在 Evidence 对象，预期差仍 `resolved`。

修复：来源引用必须能解析到当前运行的 `src-…:A…` 锚点、原始哈希和材料截止时点；验证单位、期间、归母/合并口径、证券类别和币种匹配。不能把“存在一个 Evidence 对象”当作证据有效。

门槛应按方法检查。企业整体权益价值换算每股时需要匹配的股数；已经核验的 EPS×PE、BVPS×PB 则重点核对每股指标自身口径，未必都需要额外重做股数除法。缺股数不必阻止企业价值本身的研究。

### P0：强制方法绕过适用性，授权无法承接

`router.py:60` 无条件采用 `force_method`。将示例股本口径置空，路由返回 `not_applicable`，但 `force_method='dcf'` 仍产出 `completed` 每股价值，并把拒绝原因追加到 gaps。

修复：手动选择方法只能在该方法的硬门槛通过后执行；适用性、参数与来源由现有控制器校验并固定假设版本。新增工具也必须通过 `RawEngine._authorize()` 和 `_tool_call()` 对应的授权检查。

同时区分方法状态与整个研究状态：某条相对估值路径完整，不代表财务/逻辑/市场基准已经全部核验。可选交叉方法缺失，也不应自动否定完整主方法。

### P0：凭证不支持真正重算，与主程序格式不兼容

`vouchers.build_voucher()` 没有保存完整 ValuationInput、分部/可比原始参数、参数来源及授权版本。`replay_offline()` 直接读取 `outputs`，没有调用数学计算，也没有先校验哈希。

复现：把凭证每股价值改成 999，`verify_voucher()` 检查失败，但 `replay_offline()` 返回 999。

现有系统使用 `calc:<hash>` 为键的字典，记录 `kind/inputs/formula/results/assumptions_version`；新演示文件是凭证列表，没有兼容的 kind。直接写入现有文件会破坏核验与重放。

修复：新增方法复用 `_record_calculation()`；保存完整、可序列化的模型输入和来源，按 kind 执行数学重算并比对结果。`RawTools._check_consistency()` 和 `replay_raw()` 都需新增方法分支；未知 kind 应明确“不支持复算”，不能直接复制原凭证视为通过。恢复旧 run 必须继续支持旧 kind。

### P0：相对估值的口径与边界

- `target_multiple` 无类型；相对估值兜底时总把它当 PE，金融路由则当 PB。
- EPS=-2、PE=10 仍返回 -20 且 `completed`；亏损 PE 不能当有效价格结论。
- 同业倍数取中位数，再把不同方法结果 min/max 当区间；单一 PE 路径只能得到 `[20,20]`，没有体现同业倍数分布。
- 可比公司来源没有完整进入 evidence_refs，也没有一致校验日期、盈利期间、TTM/FY/forward、异常或非正倍数。

修复：明确倍数类型与盈利基础；分方法呈现结果；用经过筛选的同类倍数分布形成区间并说明规则。EV/EBITDA 路径必须完成净债务和少数股东权益桥接。不同方法结果的包络不能冒充统计置信区间。

### P1：SOTP 与正常化盈利仍是候选原型

SOTP 把 EBITDA/收入/EBIT 倍数对应的企业价值与 NAV 对应的权益价值一起相加，再统一扣债。又把 `inp.net_debt` 与所有 `Segment.net_debt` 相加，若前者已是合并净债务，就重复扣减。总部费用、内部交易、持股比例也没有计算桥接。

复现：把示例 D 一个分部的 metric 改成未知值，程序跳过该分部，仍发布每股 4.5，状态 `partial`。这不是完整分部估值。

正常化盈利需明确 margin 是归母净利率还是经营利润率，以及收入/利润率/倍数的历史窗口。当前窗口只有提示文字。9 格敏感性虽然参与区间计算，却未存入 result.sensitivity 或凭证；结果明细无法核验。

修复这些口径前，留作 examples 中的候选演示；不对真实研究开放为默认正式估值路径。

### P1：方法宣传超过实现

- `nav.py` 没有资产清单、公允价值/资本化率、负债调整等 NAV 输入与计算。当前只支持 PB 与单阶段 DDM。
- `framework` 参数只写入凭证，不参与方法路由；不能声称价值/质量/变化三个框架已有各自完整估值模型。
- `fallbacks` 是建议列表，没有执行交叉验证或失败后的自动备选计算。
- 选择矩阵写 WACC−g≥1% 为门槛，`spread_ok()` 实际对不足 1% 只告警。
- 矩阵写缺价格即 not_applicable，实际方法通常 partial 并保留模型价值。缺现价不必阻止内在价值计算，阻止的是相对现价判断。

### P1：输入校验与 FCFF 方法边界

`forecast_years=0` 引发 IndexError；增长率为 NaN 时，输出归一化为 null 但状态仍 `completed`。非法税率也只告警，FCFFBridge.valid 仍为 True。

需要复用现有有限数值、正股数、整数年数和折现边界约束，避免新内核弱化已有校验。

FCFF 应是税后、再投资后且融资支付前的企业现金流；EBIT 路径的基本结构有专业依据。[Damodaran：Cash Flows](https://pages.stern.nyu.edu/~adamodar/New_Home_Page/littlebook/cashflows.htm)

审阅判断：`fcff_from_ocf()` 不能不问报表分类就普遍加回应计利息×(1−税率)；必须核对现金利息是否已在 OCF 中扣除、融资分类、税盾与重分类，防止重复调节。OCF 本身已有营运资本变化，不能再机械重复扣减。推荐先接 EBIT 桥接，OCF 桥接在真实附注对照验证后开放。

“不接受未经核对的 OCF−Capex”可以作为本项目的保守准入规则；“OCF−Capex 永远不可能是 FCFF”和“当期 FCFF 非正就所有 DCF 均无经济意义”不应写成普遍金融定律。当前固定正基期增长模型可以拒绝这些输入，未来显式预测转正现金流的模型另行判断。

| 报告信息类型 | 本版修复 | 按 fact/management_statement/assumption/prediction/judgment 呈现 |
| 新行情 API、跨期记忆、自动交易 | 不纳入本次最小集成 | 单独规划 |

这里的“市场基准比较”要分清：估值对现价的溢价/折价、估值对一致目标价的差异，以及经营假设对市场盈利预期的差异。现有 expectation.py 只实现第二类的数值形式，也可计算参考价差；它没有自动识别市场隐含经营预期。不要把任意 benchmark 叫一致预期，也不要把估值差叫预期收益率。

## 7. 具体改动位置

建议将经审阅的算法放入 `yantra/valuation/`，保持一个主系统包与一套权威契约。不要长期维护 dataclass 与 Pydantic 两套镜像。原始交付继续保留用于比较。

关键兼容映射：现有金额为 million、股数为 million shares；交付模块为元与股。适配器应同时转换金额与股数，比例字段不缩放，EPS/BVPS/股利每股数据按每股单位处理。现有字段 `base_fcf/growth_rate/discount_rate/years/per_share_value` 与新字段 `fcff_base/forecast_growth/wacc/forecast_years/value_per_share` 必须明确映射。来源引用应直接使用主系统锚点，不以“PDF 第N页”字符串替代可解析引用。

## 8. 合并顺序与验收

1. **先修原型的数据和数学门槛** → 验证缺失净债务不填零、来源为空不进入正式计算、负股数/NaN/非法年数被拒绝、force_method不绕过硬门槛、负盈利PE不发布。
2. **接入主系统工具、授权和凭证** → 验证相对估值或PB/DDM完整走通提案→授权→计算→独立核验→报告；参数或上游证据修改后旧估值失效；核验否决不可覆盖。
3. **接入报告和真正的离线复算** → 验证每方法重新计算结果；修改结果能被复算发现；缺基准仅显示缺口；原DCF和历史run保持兼容。
4. **使用真实材料验证最小新增路径** → 选择一只财报与可比数据齐备的标的做相对估值，一只资料不足的标的验证拒绝。可用本地数据验证数学链；若未重跑真实LLM流程，明确限定验证范围。
5. **修订项目书与发布标识** → 仅把验收通过能力列为已实现；竞品/报价/通知与许可信息补一手出处；最后更新pyproject、__version__、README和验证文档。

不要简单宣布“49+47=96项集成测试通过”：两套测试目前相互独立，47项还有缺口，也未纳入现有unittest发现机制。

如果资源不足，先做到“相对估值一个真实样本 + 一个证据不足拒绝样本 + 离线数学重算”，比一次开放所有方法更符合本版的可验收范围。

## 9. 工程边界：扩展估值子系统，保留投资逻辑架构

当前关系是：finance 提供事实 → thesis 在固定框架下形成论点、风险、反证和预期假说 → valuation 提案、授权、计算 → verification 独立核验 → report。

集成后保持同一关系，只将 valuation 从“DCF / 不适用”扩展为“按方法检查条件，执行已授权的 DCF / 相对估值 / PB / DDM”。因此是估值子系统的局部结构调整，不是投资逻辑架构重建。

`frameworks.py` 的 value/quality/change 是研究视角；DCF/PE/PB/DDM 是定量工具，两个维度不能绑定成一对一关系。同一质量框架下可用DCF或PB，依据公司结构、财务口径和证据决定。投资逻辑仍负责解释为什么选择某个假设、差异从何而来、什么证据可以推翻判断。

### 9.1 一套控制流程、一套计算入口

保留现有 `valuation` 工具名与 valuation 角色，在 RawToolRegistry 中覆盖 `_valuation()` 完成分派，不为每种估值方法新增智能体或工作流。保留原工具注册和预算统计，更新实际工具契约与描述。

推荐关系：

```text
投资逻辑成果
  → ValuationProposal(model, parameters, basis, scope, gaps)
  → 控制器按model检查方法条件、来源及参数
  → 固定授权快照(model + parameters + basis + version)
  → valuation工具检查请求与授权快照一致
  → 对应数学函数计算
  → 主系统统一结果与计算凭证
  → 独立核验与报告
```

新增数学模块只负责计算和返回结果，不负责修改运行状态、批准参数或发布报告。交付物的 router 可拆取方法判断逻辑，不能成为绕过现有控制器的第二套入口。

### 9.2 授权对象必须包括方法身份

目前 Assumptions 只有 version/confirmed/parameters/basis/authorization_source，没有model；工具调用也只检查参数与版本。若只扩展提案枚举，控制器还会把relative等方法降为not_applicable，或按DCF字段校验而拒绝。

应为假设和工具请求明确方法身份。兼容旧快照时，可把旧数据没有model解释为dcf；新研究必须保存显式model，并核对工具请求与授权一致。方法改变也必须重新授权并令旧估值和核验失效。不能仅确认一组数字，却允许计算阶段换一种方法解释它们。

参数校验按方法分支执行：

- DCF：FCFF、WACC、增长率、预测年数、净债务、股本及依据。
- PE：EPS的期间与归属口径、PE类型、可比集及日期。
- PB：BVPS与净资产口径、PB依据。
- EV/EBITDA：EBITDA与倍数、净债务和少数股东权益桥接、股本。
- DDM：每股下一期股利、股权成本、长期增长及来源。

共有校验是有限数值、证券身份、口径、截止时点、出处；方法专有校验不能继续要求所有方法必须有FCFF/WACC。

### 9.3 兼容需要主动设计

| 冲突 | 当前行为 | 集成做法 |
|---|---|---|
| 方法枚举与调度 | 仅允许dcf/not_applicable，多个提示文本也只考虑DCF | 更新schema、提案处理、自动补提案问题及工具描述；不改变角色顺序 |
| 角色与工具提示 | adk_app角色描述、backend基础指令、tools契约描述仍限定DCF | 与research的raw指令同步扩展，避免继承提示相互矛盾；保留既有角色、权限和预算 |
| 授权与手动改参 | 校验全部按DCF字段；方法不在授权快照 | 引入方法身份与按方法校验；改参/换方法沿用版本和失效机制 |
| 单位与字段 | 主系统百万货币/百万股，交付模块元/股且字段名不同 | 主接口保留现有标准，显式适配数学函数；每股指标不按总金额缩放 |
| 结果和完成状态 | Result使用complete/partial/blocked，交付结果使用completed/not_applicable等 | 方法状态放data内部，映射工作成果状态；不直接修改运行状态枚举 |
| 原文引用 | 主系统使用可解析src:A锚点，交付使用页码描述字符串 | 直接保留主系统锚点和哈希，不把自然语言位置当正式引用 |
| 凭证与重放 | 字典索引、calc:哈希、kind分派；交付是另一结构 | 主系统统一记录；按kind/schema版本重算，旧DCF算法行为保持可复现 |
| 市场预期成果 | report从thesis.expectations读取；新expectation另算一个结果 | thesis保留研究解释，计算工具提供结构化比较凭证；报告组合显示并核对同一基准 |
| 报告假设 | 渲染代码硬编码DCF和其情景字段 | 统一每方法结果外层；DCF情景、PB/DDM路径、相对估值区间分别渲染 |

尤其要区分“估值计算完整”与“研究已完成”。新增PB结果不能绕过对投资论点、反证、市场基准和独立核验的现有要求。缺估值的真实研究仍可partial。

### 9.4 投资逻辑层的最小增量

本版不需要改写ThesisData核心结构或框架存储。可以在ValuationProposal.basis内引用相关论点：哪个claim/hypothesis支持收入增长、利润率、倍数或股利假设，并保存理由、source_refs及缺口。这是论点到参数的可追溯连接，不是新的投资逻辑引擎。

首先沿用现有保守失效规则，避免同时重构依赖图。估值结果可以影响最终条件性投资判断，但不能自行篡改既有论点；需要改变论点时，走已有重新分析/修复和核验流程。

### 9.5 工程任务拆分

1. 契约与数学层：修正候选方法、加入明确model身份及统一单位；验证原DCF兼容和非法输入拒绝。
2. 控制器与工具层：更新RawEngine的提案、授权、手动改参和调用检查，RawToolRegistry分派计算；验证新方法完整执行且旧授权无法用于新方法。
3. 核验与报告层：统一凭证、按方法重算、报告渲染、市场基准与论点解释连接；验证篡改拒绝、旧run复现和缺基准降级。
4. 发布层：真实样本和原49项回归通过后，更新版本与能力说明。

上述是实施设计，不表示这些改动已经执行。
